### B1 — Mobile app logo inconsistent — **Bug, confirmed**

You called it: the green background is the problem.

- Splash/preloader logo (`apps/web/index.html` → `public/logo-mark.png`): white badge (`.logo-badge { background: #ffffff }`), logo has its natural white background.
- `public/apple-touch-icon.png`, `public/pwa-192x192.png`, `public/pwa-512x512.png`: white/cream background, consistent with each other and the splash.
- `public/maskable-icon-512x512.png`: **solid dark-green fill** (`#1B4332`-ish) behind the logo.

That last one is exactly what Android (and any launcher honoring `purpose: "maskable"` in the manifest, declared in `vite.config.js`) uses for the home-screen app icon — so the icon a user actually sees on their phone's home screen is the odd one out, and the green fill visually merges with the dark-green ring in the logo mark itself, making it read as a different shape ("something else," as you put it) instead of the crest.

**Fixed:** regenerated `apps/web/public/maskable-icon-512x512.png` from the same source artwork as the splash logo (`logo-mark.png`), composited onto a plain white background at the same safe-zone padding the old (green) version used (~56% content width, well within the maskable safe zone). Asset-only change, no code touched.

### B5 — ACHI claim (Caomi4u@gmail.com) — revised: confirmed bug, fixed

Originally logged as a duplicate of A2 (not a bug — self-registered, unverified ACHI number). The user later reported it was resolved on the LMS side but still not reflecting in the app, which reopened it.

Verified independently: a direct, read-only call to WordPress's own live verify-cert endpoint confirmed `valid: true, status: active` for his ACHI number — the LMS side really is correct. Our DB was still stale. Root cause traced to the app's own "Re-verify" button: it called the public `GET /certs/verify/:achiNumber` (`CertCacheService.verifyWithCache`), which checks WordPress live but only ever writes the result into a `cert_cache` mirror table — never into `inspector_profiles`. So the button could confirm the truth but had no way to apply it; clicking it forever showed a stale "candidate" status regardless of what WordPress said.

**Fixed:** added `CertService.reverifySelf()` + `POST /api/v1/certs/reverify` — an authenticated, inspector-only route that reads the ACHI number from the caller's own session (never client-supplied), does the same live WordPress check, and **promotes** `inspector_profiles` when WordPress confirms certified/active. Deliberately promote-only per the user's call: a WordPress response of suspended/expired/not-found/error never touches the profile — those stay on the existing authoritative paths (the WordPress webhook, admin's own verify route). Frontend now calls this instead of the old public endpoint. New tests cover the promotion case and all three non-promoting statuses.

Separately: a concurrent, uncommitted change had appeared in `apps/api/src/routes/wordpress.ts` mid-session (not made by this session) making `lms_course_id` nullable in the `cert-issued` webhook schema — directly relevant, since a certificate issued without an originating course would have been rejected outright by the old schema before ever reaching `inspector_profiles`. Confirmed correct and folded in at the user's instruction.

### B6 — Limitations not reflected in final report — **Bug, confirmed, root cause found**

The report-rendering side is actually fine — `pdf.ts` renders a `LIMITATIONS` section (lines ~728-732) whenever `limitations.length > 0`, and `ReportService.generate()` correctly fetches limitation text via the `inspectionLimitations` join table and passes it through. The problem is upstream: **nothing ever populates `inspectionLimitations` any more.**

`inspectionApi.setLimitations()` exists in `apps/web/src/lib/api.ts:878` and calls a working backend route (`PUT /inspections/:id/limitations`) — but grepping the entire frontend, it is **never called anywhere**. Found why: commit `541ee67` ("fix: remove Access Limitations section from review screen", 2026-07-02) deliberately removed the only UI that called it, on the reasoning that the old library-based "Limitations" question was redundant with the newer "Inspection Constraints" field (`InspectionMetadataForm`, captured at the *start* of an inspection instead of right before submit) — and that field *is* correctly wired through to the report today, under a section titled **"Inspection Constraints"** (not "Limitations"), on the constraints/disclaimer page.

So there are two live possibilities for what the inspector actually means, and they lead to different fixes:
1. **They mean the old admin-curated Limitation Library specifically** (the one still visible in Admin → Limitation Library) and expected to be able to pick from it. It's fully orphaned — reachable from the DB and the API, invisible from the inspector UI. Options: (a) restore inspector-facing UI for it (undoing 541ee67's premise), or (b) if Inspection Constraints really did supersede it, remove the now-dead `limitationLibraryApi`/`setLimitations` client code and the Admin screen too, so there's one library instead of two that look similar.
2. **They mean the newer Inspection Constraints and just didn't recognize the heading.** In that case nothing is broken — it's a labeling/discoverability issue, not a data-flow bug, and the fix might be as small as confirming with the inspector, or renaming the PDF section if "Limitations" is the term the business actually wants printed.

**Resolved and fixed:** the underlying system (what was being called "Inspection Constraints") was already correctly capturing and rendering data — nothing was broken there. The client's ruling settled the remaining question: the term shown to readers should be "Limitations", not "Inspection Constraints". Applied as a pure terminology change (internal field/variable names untouched, same approach as the B4 severity-label rename) across the PDF report, its section heading and table of contents, the disclaimer text (both copies — `pdf.ts` and `inspectionMetadata.ts`, which must mirror each other), the inspector's capture form label, and the in-app `ReportView.tsx`. The PDF's Limitations section was already the last page — "collated at the end" was already true there; the in-app `ReportView.tsx` version was not (it sat mid-page, before the findings) and has been moved to match. Fixed in commit `6749fc6`, with a new test (`pdf.limitations.test.ts`) confirming the document says "Limitations", never "Inspection Constraints", and that it's on the final page.

One related gap surfaced while checking this originally: **neither "Limitations" nor "Inspection Constraints" is visible anywhere in the Admin panel for a specific inspection.** `Admin/InspectionDetail.tsx` (and every other admin screen) never renders `InspectionMetadataForm` or any of its fields (building type, occupancy, attendance, limitations) — that component is only used in the inspector's own creation flow. The data is captured, stored, returned by the API, and correctly shown in the report — an admin reviewing/approving a job just can't see it without opening the generated report first. Not logged as its own numbered item yet — flagging for you to decide if it's worth tracking.

### B7 — Report filename / numbering scheme — **Feature / improvement, gap-mapped**

**What exists today:**
- Certificate number (serves as *both* internal reference and the number printed on the document): `IA-<YEAR>-<6-digit-seq>`, e.g. `IA-2026-000001`. Minted once per inspection's first approved report via an atomic per-year counter (`certNumberCounters` table, `ReportService.generateCertificateNumber()`); reused as-is across regenerated versions of the same report (version tracked separately as a plain integer in `reportVersions.version`).
- PDF filename (`apps/api/src/lib/reportFilename.ts`, `buildReportFilename()`): `InspectAfrica-<TypeAbbr>-<slugified-property-address-or-cert-number>-<YYYY-MM-DD>.pdf`, e.g. `InspectAfrica-SHI-12-Banana-Island-Road-Ikoyi-2026-08-21.pdf`.
- No `properties`/project ID concept exists anywhere in the schema — only free-text `propertyAddress` on `bookings`/`inspections`, no sequential Property/Project ID like `PRP000847`.
- **No version suffix in the filename at all** — if a report is regenerated (e.g. after a revision), the new PDF's filename can come out identical to the previous version's (same address, same day), differing only in file content. This is a real, separate gap the proposal happens to also fix.

**Gap vs. the proposal:**
| Proposed element | Exists today? |
|---|---|
| `[Company]` = "HINL" | No — filename says "InspectAfrica" (the platform name). Note: "HINL" is already the operating brand used elsewhere (inspection type names, "HINL Certified Inspector" credential label) — this is a real branding mismatch worth fixing regardless of the rest of the proposal. |
| `[InspectionType]` as a readable label (`HOME`, `CONSTRUCTION`, `SNAG`) | Partial — current filename uses the internal 3-letter code (`SHI`, `CIB`, …) not a business-readable label; would need a code→label map for filenames specifically. |
| `[PropertyID]` (`PRP000847`) | No — no structured property/project ID exists at all, only free-text address. This is the biggest gap; would need a new sequential-ID concept, not just a filename format change. |
| `[Date]` as `YYYYMMDD` | Close — today it's `YYYY-MM-DD` (dashed). Cosmetic. |
| `[ReportVersion]` (`V01`) | No — genuinely missing, and worth fixing on its own regardless of the rest (filename collisions across re-generated versions). |
| Split internal ID vs. report number | Today these are the same value (`certificateNumber`). The DB already has a stable internal identifier that never changes — the `inspections.id` UUID — so a *new* sequential internal ID (`INS-2026-0001847`) would be a third identifier alongside the UUID and the report number, which may be redundant unless there's a specific need for a human-readable internal reference distinct from both. Worth a deliberate decision, not a given. |

**Regression impact if adopted:** the PDF filename is generated fresh on every download (`Content-Disposition` header) — changing its format is purely cosmetic and safe. The certificate-number format is the one part that needs care: it's printed on every PDF already delivered to clients and stored in the DB, so any format change should apply go-forward only — old `IA-2026-NNNNNN` numbers must keep resolving/displaying correctly, not get renumbered.

### B8 — Photo upload shows camera-only in installed PWA, works on web — **Bug, confirmed**

This is a well-known behavior split for the HTML file-input `capture` attribute, and this codebase hits it directly. Found exactly two places using it:

- `apps/web/src/screens/Inspector/SectionDetail.tsx:147` — condition/observation photo upload (the one you're describing).
- `apps/web/src/components/CoverCaptureSheet.tsx:101` — the inspection's "Front view photo" cover shot.

Both use `<input type="file" accept="image/*" capture="environment" />`. In a normal browser tab, `capture` is only a *hint* — mobile browsers still show the full picker (Camera, Photo Library/Gallery, Files). But in an **installed, standalone PWA** — the actual primary way inspectors are meant to use this app in the field — several mobile browser/OS combinations (notably iOS Safari's standalone mode, and some Android installed-PWA contexts) treat `capture` as a stronger directive and jump straight to the camera, skipping the chooser entirely. That's exactly the asymmetry you're seeing: works on laptop/web, camera-only once installed.

We already established (earlier in this session) that there's no policy or server-side reason condition/observation photos need to come from a live camera capture — gallery upload is already effectively permitted by design, just not reliably *offered* once installed. So this is a straightforward bug, not a security control being worked around.

**Fixed:** dropped `capture="environment"` from `SectionDetail.tsx`'s file input — `accept="image/*"` alone still lets mobile browsers default to opening the camera as the *first* option in the chooser on most devices, it just stops forcing it as the *only* option, restoring the gallery choice in both contexts.

`CoverCaptureSheet.tsx`'s cover photo has the same root cause but was **left as-is** — the UI already labels it "(recommended)" and is skippable, so it's not a strict live-capture requirement either, but if the intent there actually *is* "prove the inspector is on-site right now," removing `capture` would undercut that on purpose. Flag if you want that one changed too.
